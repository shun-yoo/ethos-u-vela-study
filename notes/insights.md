# Insights

공부하며 얻은 핵심 인사이트. 자세한 설명은 링크한 노트에 있다.

1. **컴파일러는 최적을 보장하지 않는다.** 결정의 경우의 수가 너무 많고 후보를 실제로 실행해 볼 수 없어서, 휴리스틱과 비용 모델로 대체로 좋은 결과를 고른다. Vela 스케줄러도 SRAM에 들어가는 가장 큰 조각을 고를 뿐, 후보들의 사이클을 서로 비교하지 않는다.
   → [00 1.2절](00-compiler-and-model-basics.md), [04](04-scheduling.md)

2. **NPU에는 캐시가 없어서, 타일링·연산 융합·이중 버퍼링이 백엔드의 자원 할당 문제가 된다.** CPU에서는 캐시 회로가 빠른 메모리를 관리하므로 이런 변환이 접근 순서 최적화로서 미들엔드에서 다뤄질 수 있다. Ethos-U에서는 어떤 데이터를 SRAM 어디에 언제 둘지를 컴파일러가 DMA 명령으로 정해야 하므로, SRAM 크기·할당 상태·DMA 속도를 아는 백엔드에서 함께 정해야 한다.
   → [04 Insight](04-scheduling.md)

3. **성능 면에서 백엔드가 하는 일은 옮기는 데이터 줄이기, 연산기 활용 높이기, 데이터 이동과 계산 겹치기로 나눠 볼 수 있다.** Vela의 비용 모델은 연산마다 max(NPU 처리 시간, 메모리 접근 시간)를 구해 모두 더하는 방식으로 실행 시간을 추정한다.
   → [04 성능을 위해 백엔드가 하는 일](04-scheduling.md)
