# 컴파일러와 딥러닝 모델 기초

## 1. 컴파일러의 기본 구조

### 1.1 프론트엔드·미들엔드·백엔드

컴파일러는 사람이 작성한 프로그램을 특정 하드웨어가 실행할 수 있는 형태로 바꾸는 프로그램이다.

- 바꾸는 도중에 프로그램을 직접 다루지 않고, 다루기 쉬운 자료구조로 옮겨서 작업한다.
- 이 자료구조를 **IR**(Intermediate Representation, 중간 표현)이라고 한다.
- 컴파일러는 보통 IR을 기준으로 세 부분으로 나뉜다.

| 부분 | 하는 일 | 하드웨어와의 관계 |
|---|---|---|
| 프론트엔드 | 소스 코드를 읽고 문법을 분석해서 IR로 바꾼다. | 무관 |
| 미들엔드 | IR에서 결과는 같으면서 더 효율적인 형태로 바꾼다. 예: 결과가 쓰이지 않는 계산 제거, 상수끼리의 계산을 미리 해 두기 | 대체로 무관 |
| 백엔드 | 특정 하드웨어에 맞춘다. 어떤 기계 명령을 쓸지 고르기, 한정된 저장 공간(레지스터)을 값들에 나눠 주기(할당), 명령 순서 정하기, 최종 명령 생성 | 직접 관련 |

이렇게 나누면 하드웨어가 바뀌어도 백엔드만 새로 만들면 된다.

### 1.2 최적화 결정의 한계: 최적 보장 대신 휴리스틱과 비용 추정

**컴파일러가 내리는 결정**

같은 계산이라도 실행하는 방법은 여러 가지다. 컴파일러는 그중 하나를 골라야 한다. 예를 들면 다음과 같은 결정들이다.

- 반복문이나 텐서를 어떤 크기의 조각(타일)으로 나눌지
- 어떤 데이터를 빠른 메모리에 둘지
- 어떤 연산들을 묶어서 실행할지
- 어떤 순서로 실행할지

**최적을 찾기 어려운 이유**

1. **경우의 수가 너무 많다.**
   - 결정들이 서로 얽혀 있어서 따로따로 정할 수 없다.
   - 예: 한 레이어의 조각 크기를 키우면 메모리를 더 쓰게 되고, 그만큼 옆 레이어가 쓸 수 있는 메모리가 줄어든다.
   - 그래서 레이어마다 후보가 몇 개씩만 있어도, 레이어가 수십 개면 전체 조합 수는 레이어별 후보 수를 모두 곱한 만큼 늘어난다.
2. **후보 하나를 평가하는 데도 비용이 든다.**
   - 가장 정확한 평가는 실제 하드웨어에서 실행해 시간을 재는 것이다.
   - 하지만 컴파일 중에 모든 후보를 실행해 볼 수는 없다. 대상 하드웨어가 컴파일하는 PC에 없는 경우도 많다.

**그래서 컴파일러가 쓰는 방법**

| 방법 | 설명 |
|---|---|
| 휴리스틱 | 경험적으로 대체로 맞는 규칙으로 후보를 줄이거나 바로 고른다. 예: "메모리에 들어가는 한 조각은 클수록 좋다" |
| 비용 모델 | 실행하지 않고, 하드웨어 특성(연산기 수, 메모리 속도 등)을 넣은 계산식으로 사이클과 메모리 사용량을 추정한다. |

**보장되는 것과 보장되지 않는 것**

- **보장되는 것: 정확성.** 바꾼 프로그램의 계산 결과는 원래와 같고, 하드웨어 제약(메모리 크기 등)을 지킨다.
- **보장되지 않는 것: 최적성.** 원인은 세 가지다.
  1. 탐색 제한: 가능한 조합을 모두 시도하지 않는다.
  2. 휴리스틱의 가정: 규칙이 맞지 않는 경우가 있을 수 있다.
  3. 비용 모델의 오차: 추정치가 실제 하드웨어와 다르면, 판단도 어긋난다.

**최적에 더 가까이 가려는 접근: 자동 튜닝**

- 후보를 실제 하드웨어에서 측정하면서 탐색하는 방법도 있다.
- TVM의 MetaSchedule이 그 예다. 측정 결과로 비용 모델을 학습시키면서 더 좋은 후보를 찾아간다.
- 결과는 좋아지지만, 컴파일(튜닝)에 시간이 오래 걸리고 측정할 하드웨어가 있어야 한다.

**결과가 좋은지 확인하는 방법**

컴파일러의 결정이 좋은지는 코드를 읽는 것만으로는 알 수 없다. 측정해야 한다.

- 비용 모델의 추정치와 실제 실행 결과를 비교한다.
- 설정을 바꿔 가며 결과가 기대대로 변하는지 본다.
- 작은 문제에서는 후보를 모두 직접 시도해 보고, 컴파일러의 선택과 비교한다.

Vela에서의 구체적인 예는 [03-scheduling.md](03-scheduling.md)에 있다.


## 2. 딥러닝 모델과 컴파일러의 입력

### 2.1 학습된 모델과 모델 파일(.tflite)

**딥러닝 모델**

- 딥러닝 모델은 합성곱, 덧셈, 활성화 함수 같은 **연산**들을 연결한 계산 구조다.
  - 활성화 함수의 예로 ReLU가 있다. 음수를 0으로 바꾸는 함수다.
- 연산 사이를 흐르는 데이터는 **텐서**(다차원 배열)다.
  - 예: 224×224 컬러 이미지 한 장은 1×224×224×3 텐서다.
- 학습을 통해 각 연산의 **가중치**(합성곱 필터 값 등)가 정해진다.
- 학습이 끝나면 가중치는 고정되고, 이후에는 입력을 넣어 출력을 계산하는 **추론**만 한다.

**모델 파일**

- 학습한 모델은 파일로 저장해서 다른 도구로 넘긴다.
- **.tflite**는 TensorFlow Lite 형식의 모델 파일이다.
  - TensorFlow Lite는 Google이 만든, 모바일·임베디드 기기용 추론 형식이자 실행 라이브러리다. 2024년에 LiteRT로 이름이 바뀌었지만 파일 형식(.tflite)은 그대로다.
- **만들어지는 경로:** TensorFlow 모델을 **TFLite 변환기**(TensorFlow에 포함된 변환 도구)에 넣으면 .tflite 파일이 나온다. PyTorch 모델은 별도의 변환 도구(예: Google의 AI Edge Torch)를 거쳐 .tflite로 만든다.
- **파일 안에 든 것**

  | 내용 | 설명 |
  |---|---|
  | 연산 그래프 | 어떤 연산을 어떤 순서로, 어떤 텐서끼리 연결해 실행하는지 |
  | 텐서 정보 | 각 텐서의 모양(예: 1×112×112×32)과 자료형(int8 등) |
  | 가중치 | 학습으로 정해진 값. 파일 용량의 대부분을 차지한다. |
  | 양자화 정보 | 정수값을 실수값으로 해석하는 데 쓰는 텐서별 scale과 zero point |

**int8 양자화**

- 32비트 실수(float32)로 된 가중치와 텐서 값을 8비트 정수(int8)로 바꾸는 것이다.
- 원래 실수값은 대략 `scale × (정수 − zero_point)`로 복원된다.
- 효과: 메모리가 4분의 1로 줄고, 정수 연산기로 계산할 수 있게 된다.
- 소형 NPU 중에는 양자화된 모델만 실행할 수 있는 것이 많다. Ethos-U도 그렇다.

**실습에 쓰는 예시 모델: MobileNet v2 (int8)**

- 출처: Arm이 공개한 모델 모음인 ML-Zoo에서 받은 `mobilenet_v2_1.0_224_INT8.tflite`
- 하는 일: 이미지 분류. 224×224 컬러 이미지를 입력받아 ImageNet의 약 1000개 클래스별 점수를 출력한다.
- 구조: 모바일 기기용으로 계산량을 줄인 CNN(합성곱 신경망)이다.

### 2.2 모델 파일은 컴파일 과정의 어디까지 와 있는가

.tflite 파일에는 연산 그래프가 이미 들어 있다. 1.1의 세 부분에 대응시키면, 프론트엔드는 끝났고 미들엔드도 일부 끝난 상태다.

| 일반 컴파일러 | 딥러닝 모델의 경우 | 담당 |
|---|---|---|
| 프론트엔드 | 프레임워크(PyTorch, TensorFlow)로 정의한 모델을 연산 그래프로 만든다. | TFLite 변환기 |
| 미들엔드 (일부) | 그래프를 정리하고 양자화한다. (아래 목록 참고) | TFLite 변환기 |
| 미들엔드 (나머지, 하드웨어 맞춤) | 대상 NPU가 지원하는 형태로 연산을 바꾸거나 쪼개거나 합친다. | NPU 컴파일러 (Vela) |
| 백엔드 | 실행 방식과 순서를 정하고(스케줄링), 메모리를 할당하고, 하드웨어 명령을 생성한다. | NPU 컴파일러 (Vela) |

TFLite 변환기가 미들엔드 단계에서 하는 일은 다음과 같다.

- 배치 정규화를 앞의 합성곱 가중치에 합쳐 넣는다. 배치 정규화는 학습을 안정시키려고 넣는 정규화 연산인데, 추론 때는 상수 계산이 되므로 합칠 수 있다.
- ReLU 같은 활성화 함수를 앞 연산의 속성으로 붙인다.
- 상수끼리의 계산을 미리 해 둔다.
- int8 양자화를 한다.

정리하면, .tflite 파일은 일반 컴파일러로 치면 "프론트엔드와 일부 최적화를 거친 IR"에 해당한다.

**그래프가 정해졌다고 실행 방법까지 정해진 것은 아니다**

그래프에 정해진 것은 **무엇을** 계산하는가뿐이다. **어떻게** 실행하는가는 정해지지 않았다.

- 예: MobileNet v2의 첫 합성곱 출력 텐서(112×112×32, int8 기준 약 392KB)를 칩 안의 작은 메모리에 한꺼번에 둘지, 잘라서 둘지
- 예: 가중치를 바깥 메모리에서 언제 가져올지
- 예: 연속된 두 연산을 번갈아 조금씩 실행할지

이 "어떻게"를 대상 하드웨어에 맞게 정하는 것이 NPU 컴파일러의 일이다.

**범용 딥러닝 컴파일러(TVM)와의 범위 비교**

- TVM은 여러 형식의 모델(PyTorch, ONNX 등)을 직접 받아 자기 IR로 바꾼다. 즉 프론트엔드도 직접 한다.
- 이어서 그래프 수준 최적화(미들엔드)와 연산 하나 수준의 코드 생성(백엔드)까지 직접 한다.
- 반면 Vela는 .tflite를 받아 하드웨어 맞춤 부분과 백엔드만 맡는다. 담당 범위가 TVM보다 좁다.
